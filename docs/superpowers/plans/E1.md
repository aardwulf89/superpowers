# E1: Rebase the fork onto pcvelz/superpowers dev Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build branch `rebase/pcvelz` from pcvelz `dev` with every feature of this fork rebuilt on it in pcvelz's terms, as spec E designs.

**Architecture:** Each change from the archived `main` is rebuilt against pcvelz's own text, one feature at a time. It is not replayed commit by commit. Most tasks edit Markdown skills and pin the result with grep-based text tests. Two tasks change code: `record.py` (E2/E3) and one example hook. Hooks are tested by feeding them JSON on stdin.

**Tech Stack:** Markdown skills, bash, Python 3 standard library, git, `jq`, mikefarah `yq` (for `scripts/bump-version.sh`).

**Spec:** `docs/superpowers/specs/E.md`

## Global Constraints

- **Workspace:** Claude Code's native worktree, per spec B's ruling that everything uses `EnterWorktree`. `EnterWorktree` with a name branches from `HEAD` (`main`), so create the branch and worktree first, then enter it by path. From the main checkout, as two plain commands: `git branch rebase/pcvelz f189a6f`, then `git worktree add .claude/worktrees/rebase-pcvelz rebase/pcvelz`. Then call `EnterWorktree` with `path` set to that worktree. Never commit to `main`. Never force-push.
- **"The archived `main`"** is this repo's `main` branch. Read our changes with `git diff 22f0b46 main -- <path>`, and read our files with `git show main:<path>`.
- **Every pcvelz divergence from obra stays.** Change pcvelz text only where a task says so.
- **Skill references** use the namespace `superpowers-extended-cc:<skill>`. None says `superpowers:<skill>`.
- **Ids:**
  - spec letter `K`, plan/phase `K3`, task `K3.4`, split parts `K3.4a` and `K3.4a1`;
  - commit subjects `feat(E1.n): …`;
  - never padded, never a fixed width.
  - No hook or regex may encode the id grammar. Its one definition is `skills/brainstorming/scripts/next-spec-id`.
- **Shell commands in skill text** that may run inside an `EnterWorktree` worktree are plain, one per Bash call:
  - no `&&`, `;`, `$(…)` or heredoc around git;
  - no `cd <main> && git …`;
  - no `git -C <main checkout>` from inside the worktree.
- **Wording:** the style of the archived `main`'s text: short declarative sentences, "your human partner", one rule per bullet.
- **Zero third-party dependencies.** `record.py` stays standard-library Python.
- **Tasks follow spec E § 4's three rules:**
  1. a task is a work task if and only if it carries a `json:metadata` block;
  2. a skill touches only its own tasks;
  3. tasks live for one session.
- **Step-task titles** are `<name> (<id>)`, with the name first.
