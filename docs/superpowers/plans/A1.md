# A1: Reference-style ids Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every spec, phase and task one reference-style id (`K`,
`K3`, `K3.4`) that is unique across the repo, never reused, and written
in full everywhere a spec, phase or task is named. Splits are defined at
every point they can happen.

**Architecture:**
- **One new script:** `skills/brainstorming/scripts/next-spec-id` issues
  spec letters, and phase numbers with `--phase`.
- **One script change:** `task-brief` treats second-level split parts as
  sub-tasks.
- **Each skill owns the level of id it issues and states it in its own
  words:**
  - brainstorming: spec letters;
  - writing-plans: plan ids and task ids;
  - chaining-plans: phase ids and the phase split and merge rules;
  - the two executors: their own forms and the during-the-build split
    rule.
- **A static check, `tests/reference-ids/test-reference-ids.sh`,** pins
  the forms each skill must and must not contain. Each prose task adds
  its section to it first (RED), then edits the skill (GREEN).

**Tech Stack:** Markdown skill files, bash, awk, git, jq. Tests are bash,
plus headless `claude -p` for the chaining-plans integration tests.

**Spec:** `docs/superpowers/specs/2026-11-13-reference-style-ids-design.md` (spec A)

## Global Constraints

- **Grammar, verbatim from the spec:**
  ```
  spec    = UPPER+                  letters A–Z, skipping I and O
  phase   = spec NUM part*          K3, K3a, K3a1
  task    = phase "." NUM part*     K3.4, K3.4a, K3a.2
  part    = lower+ | NUM            alternating after the number: 3, 3a, 3a1, 3a1b
  NUM     = [1-9][0-9]*             no zero-padding
  lower   = a–z, skipping i, l and o
  ```
  Spec letters go `A, B, … H, J, … N, P, … Z, AA, AB, …`, skipping I and
  O at every position.
- **Terms used in skill text:**
  - **plan id:** the plan's phase id (`K3`), from the plan's first line
    `# K3: …`.
  - **task id:** the id after `Task` in a plan heading (`K3.4`).
  - **`<id>`** in executor forms means the task's id as its plan
    heading writes it: `K3.4` in a plan with ids, `3` in one without. A
    plan without ids has no plan id, and a line that would start with
    `<plan id>:` starts bare.
- **Files are named by id only:**
  - `docs/superpowers/specs/K.md`, first line `# K: <Title>`;
  - `docs/superpowers/specs/K3.md` (a phase design), first line
    `# K3: <Title>`;
  - `docs/superpowers/plans/K3.md`, first line
    `# K3: <Feature Name> Implementation Plan`.
- **Task headings keep the word `Task`:** `### Task K3.4: <Component Name>`.
- **Commit subjects carry the narrowest id.** In a conventional-commit
  repo it is the scope (`feat(K3.4): …`); otherwise the subject starts
  `K3.4: …`.
  - a task's commits use the task id;
  - the final review's fixes, the deferred-findings round, and a phase's
    design, plan or Phases-section docs use the phase id;
  - a spec, and Create's Phases section, use the spec letter.
- **Ledger forms keep their shapes,** with ids:
  - `Task <id>: complete …`, `Task <id>: Ruling: …`,
    `Task <id>: parked — … — Ruling: …`;
  - `<plan id>: Ruling: …` for a ruling about no single task;
  - `<plan id>: Final: …` for every line that today starts `Final:`.

  Every ruling line still contains `Ruling:`.
- **Unchanged:**
  - the ledger's first line;
  - the SDD workspace path, which is keyed by the plan basename;
  - the record's shape (ten keys per phase);
  - the code of the record commands in `record.md`. Only its prose and
    examples change.
- **Docs that predate the scheme keep their dated names.** Nothing is
  renamed.
- **Scripts:**
  - bash, mode `100755` (`git update-index --chmod=+x`);
  - clean under `scripts/lint-shell.sh <files>`.
- **Every skill line that runs `next-spec-id`** by a relative
  `scripts/…` path also says "by its absolute path", like the SDD
  helpers (`tests/sdd-helper-paths`).
- **Voice:** "your human partner".
- **Editing:** skills are edited by hand, not with `writing-skills`.
- **Skill size:** `tests/skill-size/test-skill-size.sh` does not gate
  this plan. Your human partner said to ignore skill-length warnings, and
  SDD's `SKILL.md` is already over the limit. Do not trim content to fit.
- **No version bump.** It happens at push, not in this plan.
- **Every commit message ends with**
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A specs or plans directory holding a non-id doc** (`README.md`
   whose first line is `# README`, a dated legacy spec): `next-spec-id`
   must not count it as a letter. Test: A1.1.
2. **A worktree whose branch is behind `base`,** where `base` already
   has spec `K`: `next-spec-id` must still print `L`. Test: A1.1.
3. **A requested task id that is a digit-prefix of another**
   (`K3.4` vs a deeper `K3.41`): `task-brief` must not fold K3.41 into
   K3.4's brief. Test: A1.2.
4. **A legacy plan with `### Task 3` headings run by either executor:**
   the forms fall back to the bare heading id, and no `K` is invented.
   This is pinned by the "as its plan heading writes it" text (A1.4,
   A1.5) and by `task-brief`'s existing tests still passing (A1.2).
5. **A phase or task split twice** (K2a → K2a1, K3.4a → K3.4a1): the
   record rule and `task-brief` both handle the second level. Test:
   A1.2 for tasks; A1.6's check pins `K2a1` in `record.md`.

### Task A1.1: `next-spec-id`

**Files:**
- Create: `skills/brainstorming/scripts/next-spec-id` (mode 100755)
- Create: `tests/next-spec-id/test-next-spec-id.sh`
- Modify: `tests/sdd-helper-paths/test-sdd-helper-paths.sh` (add
  `next-spec-id` to the helper alternation in `invocation`, and to the
  header comment's list)

**Interfaces:**
- Produces:
  `next-spec-id [--base <branch>] [--phase <letter>] [<specs dir> [<plans dir>]]`.
  - Runs from anywhere inside a git working tree, and acts on that tree,
    like git.
  - With no options it prints the next spec letter (`K`). With
    `--phase K` it prints the next phase id of spec K (`K4`). It prints
    one line and exits 0.
  - It exits 2, with a message on stderr, on bad usage or outside a git
    repo.
  - The dirs default to `docs/superpowers/specs` and
    `docs/superpowers/plans`, relative to the repo root.
  - `--base` defaults to `refs/remotes/origin/HEAD`'s branch, else
    `main`, else `master`. With none of these present, only the working
    tree is read.
- **A doc's id** is read from its first line only:
  `^# (<id>):`, where `<id>` matches the grammar's spec, phase or task
  form. Its **letter** is the leading uppercase run. A letter containing
  I or O is not an id. File names are never read. This is a ruling:
  the spec also counts file names, but `README.md` would read as spec
  `README`.
- **The docs read:** every `*.md` directly in either dir, in the working
  tree and in `base`'s tree (`git ls-tree --name-only <base> -- <dir>/`,
  then `git show <base>:<path>`, taking the first line).
- **Records:** every directory under `<main checkout>/.superpowers/chain/`
  whose name is a valid letter is used. The main checkout is the parent
  of `git rev-parse --path-format=absolute --git-common-dir`. For
  `--phase K`, so is every `.phases[].id` in `.superpowers/chain/K/effort.json`.
- **Spec mode:** print the letter after the highest used one. Order is
  by length, then by position in `ABCDEFGHJKLMNPQRSTUVWXYZ`. Gaps are
  never refilled. With none used, print `A`.
- **Phase mode:** take the highest leading number among used phase ids
  whose letter is exactly K. That covers doc first lines (`# K3: …`,
  `# K3.4: …`) and record ids (`K2a` counts as 2). Print K plus one more
  than it, or `K1` with none.
